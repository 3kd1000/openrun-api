## ✅ 매우 좋은 제안

### 1. 성별 정보 추가 및 필터링
**👍 Why Good**:
- 실제 테니스 클럽 운영에서 자주 나오는 니즈
- 여성 전용 클럽, 남복/여복 구분은 실용적
- DB 스키마 설계가 간단하고 명확함

**✅ 최종 확정 사항 (2026-01-17)**:
- **성별 선택지**: 남자 / 여자 / 비공개 (3개)
- **CTA 페이지에서 필수 선택** (비공개 포함)
- **비공개를 하나의 타입으로 취급** → 프라이버시 보호

**⚠️ 고려사항**:
- 성별 정보는 민감 정보이므로 **개인정보처리방침 업데이트 필요**
- 기존 사용자는 `PRIVATE` 기본값으로 마이그레이션
- 첫 로그인 시 성별 선택 유도 (CTA 페이지)

**📝 최종 스키마**:
```sql
-- users 테이블
ALTER TABLE users ADD COLUMN gender VARCHAR(10) NOT NULL DEFAULT 'PRIVATE';
COMMENT ON COLUMN users.gender IS '성별 (MALE, FEMALE, PRIVATE)';

-- schedule 테이블 (게스트 모집 필터)
ALTER TABLE schedule ADD COLUMN guest_gender_filter VARCHAR(20) DEFAULT 'MIXED';
COMMENT ON COLUMN schedule.guest_gender_filter IS '게스트 모집 성별 필터 (MALE_ONLY, FEMALE_ONLY, MIXED)';

-- club 테이블 (클럽 가입 제한)
ALTER TABLE club ADD COLUMN gender_restriction VARCHAR(20) DEFAULT 'NONE';
COMMENT ON COLUMN club.gender_restriction IS '클럽 가입 성별 제한 (NONE, MALE_ONLY, FEMALE_ONLY)';
```

### 2. 클럽 활동성 지표
**👍 Why Good**:
- 신규 회원이 클럽 선택 시 매우 유용한 정보
- "유령 클럽" vs "활발한 클럽" 구분 가능
- 데이터 기반 의사결정 지원

**✅ 최종 확정 사항 (2026-01-17)**:
- **배치 실행 시간**: 매일 새벽 3시 (기존 "일정 자동 정리" 배치와 통합)
- **지표 형식**: **"생성된 00개의 일정에 총 000명이 참여했습니다"**
- **유령 클럽 판단**: 일정 수 대비 참여자 수가 현저히 적으면 자동 판단
- **대진 생성 여부는 제외** (6인 이상만 가능하므로 공정하지 않음)

**⚠️ 구현 전략**:
- 실시간 집계 ❌ → **배치 작업으로 주기적 업데이트** ✅
- `club_statistics` 테이블 별도 생성 (비정규화)
- 최근 3개월 데이터만 집계 (성능 최적화)
- 참여자 수는 중복 포함 (한 사람이 10번 참여하면 10명으로 카운트)

**📝 최종 스키마**:
```sql
CREATE TABLE club_statistics (
    club_id BIGINT PRIMARY KEY REFERENCES club(id),
    total_members INT DEFAULT 0,
    schedules_count_3months INT DEFAULT 0,           -- 최근 3개월 일정 수
    participants_count_3months INT DEFAULT 0,        -- 최근 3개월 총 참여자 수 (중복 포함)
    last_updated_at TIMESTAMP,
    CONSTRAINT fk_club FOREIGN KEY (club_id) REFERENCES club(id)
);
COMMENT ON COLUMN club_statistics.schedules_count_3months IS '최근 3개월 생성된 일정 수';
COMMENT ON COLUMN club_statistics.participants_count_3months IS '최근 3개월 참여한 총 인원 수 (중복 포함)';
```

**📊 UI 표시 예시**:
- "최근 3개월 **15개 일정 / 총 120명 참여**" (활발한 클럽)
- "최근 3개월 **8개 일정 / 총 20명 참여**" (조용한 클럽)

→ 참여자/일정 비율로 활동성 자동 판단 가능!

### 3. 모집 안내문 placeholder 개선
**👍 Why Good**:
- UX 개선의 정석 (사용자가 무엇을 입력해야 할지 명확히 제시)
- 구현 난이도 낮음, 효과 즉각적

**📝 구체적인 예시 제안**:

```tsx
// 게스트 모집
placeholder={
  editingRecruitType === "guest"
    ? "예시) NTRP 3.5 이상, 구력 2년 이상 환영\n주차 가능, 라켓 대여 불가"
    : "예시) 4vs4 교류전 예정 (오후 2시~6시)\n평균 구력 3년, 복식 중심\n장소: 강남테니스클럽"
}
```

**추가 아이디어**:
- 입력창 위에 **"작성 가이드"** 버튼 추가
  - 클릭 시 예시 템플릿 제공
  - "게스트 환영 메시지 예시 3가지" 모달 표시

## 🤔 신중히 검토 필요

### 5. 클럽장 권한 양도
**👍 Why Good**:
- 실제 운영에서 필요한 기능
- 클럽 생명주기 관리에 필수

**⏸️ 상태**: 보류 (2026-01-17) - 조금 더 고민 후 결정

**⚠️ 중요 고려사항**:
1. **양도 후 되돌릴 수 없음** → 확인 프로세스 강화 필요
   - 2단계 인증 (비밀번호 재입력 또는 확인 메시지)
   - "정말로 클럽장 권한을 양도하시겠습니까? 이 작업은 되돌릴 수 없습니다."

2. **양도 대상자 동의** 받기
   - 일방적 양도보다는 "요청 → 수락" 프로세스 권장
   - 대상자가 거부할 수 있는 옵션 제공

3. **감사 로그(Audit Log) 필요**
   - 누가, 언제, 누구에게 양도했는지 기록
   - 분쟁 발생 시 증거자료

**📝 추천 플로우**:
```
1. 클럽장이 "클럽장 양도" 클릭
2. 클럽 멤버 목록에서 대상자 선택
3. 비밀번호 재입력 확인
4. 대상자에게 알림 발송 (Firebase Cloud Messaging 또는 인앱 알림)
5. 대상자가 수락하면 권한 양도 완료
6. audit_log 테이블에 기록
```

## 🎯 실용적 조언

### 1. 성별 필터는 "선택 사항"으로
- 필수로 하면 사용자 이탈 우려
- 입력 안 한 사용자는 "MIXED" 또는 "전체" 취급

### 2. 클럽 통계는 캐싱 필수
- 매번 COUNT 쿼리는 성능 저하
- Redis 또는 DB 테이블에 캐시
- 배치 작업으로 주기적 업데이트

### 3. placeholder는 간결하게
- 3줄 이내 권장
- 너무 길면 오히려 읽지 않음

### 4. 클럽장 양도는 "요청-수락" 모델
- 일방적 양도는 분쟁 소지
- 대상자 동의 받는 프로세스 추가

### 5. 비로그인 UX는 후순위
- 현재는 로그인 사용자 중심으로 운영 중
- 트래픽 증가 후 검토해도 늦지 않음
